# Fill the generation gaps

Read this file when the task is to write the hand-written code of a
generated app. A **generation gap** is an element of the definition that
a binding cannot generate, for example the logic of a custom operation.
The generator writes an **extension file** for it: a stub with a
`TODO(appgen):` comment, and a `@trace:gap` trace in its header. The
generated code next to it calls the stub, so the app builds before you
write the code.

## Steps

1. List the open gaps: `appgen check app.yaml <dir> --format json`.
   Each entry of `gaps` has the element `id`, its `kind`, and `traces`:
   the `file` and the `line` of each gap trace. The file is the
   extension file of the gap.
2. Read the element in the definition. The ID gives the path of keys,
   for example `operations.cancel_booking` is the key `cancel_booking`
   of `operations`. Read its `description`, its `entity`, its `params`,
   and its `returns`.
3. Open the extension file, and read the generated file next to it (the
   same name with `.gen.` or `_gen.py`). The generated file shows what
   calls the stub, and what the stub gets and must return.
4. Write the code in the extension file. Keep the name of the export and
   its parameters and return type, because the generated code calls it.
   Rename a parameter that you use from `_record` to `record`.
5. Remove the stub markers: the `TODO(appgen):` comment, and the
   `throw new Error("Not implemented yet: ...")`,
   `raise NotImplementedError(...)`, or the "Not implemented yet" note of
   a component.
6. In the header, change `@trace:gap <element ID> file` to
   `@trace:manual <element ID> file`.
7. Check again: `appgen check app.yaml <dir> --format json`. The element
   is not in `gaps` any more, and `invalid` and `gaps_to_close` are
   empty.
8. Build and test the app with the commands of its binding below.

`gaps_to_close` lists a gap file without stub markers that still has a
`@trace:gap` trace. If the code is done, do step 6 for it. A gap that
stays open does not fail the check.

## Rules

- Write code only in extension files: the files whose first line is
  `Created by appgen once. appgen never changes or deletes this file.`
  Their names have `.ext.` or end with `_ext.py`.
- Do not edit a generated file (first line
  `Generated by appgen. Do not edit: change the app definition instead.`).
  If the code needs a change of a generated file, for example a new
  field, change the definition, generate again into the same folder, and
  then write the code.
- Keep the header of the extension file: the first line and the trace
  line.
- New files (helpers and tests) are permitted. appgen does not change a
  file that it did not write. If new code covers an element, give it a
  trace in a comment of its own line, for example
  `// @trace:manual operations.cancel_booking`. Use only IDs that the
  definition has, and never a `generated` trace (`@trace <ID>`).
- Do not run `appgen generate --force`: it overwrites the manual edits
  of generated files.

The names in the paths below come from the names of the elements: kebab
case in the front ends (`cancel_booking` gives `cancel-booking`), and
the names of the definition in the FastAPI app. `<slice>` is the plural
of the entity in snake case, for example `bookings`.

## Next.js

| Gap                                                                | Extension file                                            | The generated code gives                                   |
| ------------------------------------------------------------------ | --------------------------------------------------------- | ---------------------------------------------------------- |
| A custom operation (`kind: custom`)                                | `src/features/<operation>/api/<operation>.ext.ts`         | `record` (the record of the entity), and `params` if the operation has `params`. Return the record of `returns`, or nothing. |
| A custom page content (`content: { custom: true }`)                | `src/pages/<page>/ui/<page>-content.ext.tsx`              | `params` (the path parameters) for a page with an entity.   |
| A custom tab of a detail view (`custom: true`)                     | `src/widgets/<view>/ui/<tab>-tab.ext.tsx`                 | `record`.                                                   |
| A custom section of a detail view (`custom: true`)                 | `src/widgets/<view>/ui/<section>-section.ext.tsx`         | `record`. A section in a tab has the name `<tab>-<section>`. |
| A custom dashboard widget (`kind: custom`)                         | `src/widgets/<dashboard>/ui/<widget>-widget.ext.tsx`      | Nothing. Load the data in the component.                    |
| A custom form widget (`widget: custom`)                            | `src/features/<form>-form/ui/<field>-widget.ext.tsx`      | `id`, `value`, `onChange`, and `disabled`.                  |
| A custom form rule (`kind: custom`)                                | `src/features/<form>-form/model/<rule>-rule.ext.ts`       | The values of the form. Return `true` if they are valid.    |
| A custom action (`kind: custom`)                                   | `src/features/<owner>-actions/model/<action>-action.ext.ts` | The record of a row action or of a page with a record, the records of a bulk action (`bulk-<action>`), or nothing. A row action has the name `row-<action>`. `<owner>` is the view, the page, or the layout. |
| The delivery of the messages of the sign-in (`auth.password_reset`, `auth.sign_up.verify_email`) | `src/shared/auth/messages.ext.ts` | `deliverMessage(message)`: send the message to `message.to`, for example by email. The generated `Message` has the `kind` (`password-reset` or `email-verification`), the `userId`, the `subject`, the `text` (in the language of the request, with the link), and the `link`. The stub writes the link to the log with `ENVIRONMENT=development`, and else throws an error. For plain emails, select `auth.delivery: smtp` in the definition instead: the app then sends them by SMTP and has no such file. |

- The binding covers all kinds of elements. A kind that a later version
  of the DSL adds, before the binding covers it, gets a gap file
  `src/gaps/<element>.ext.ts`. Write the code there, or in a better
  place with the same trace. Then change the kind of the trace from
  `gap` to `manual`.
- An operation runs on the server (`import "server-only"`). Read and
  change the data with the repositories of
  `@/entities/<entity>/server`, for example `bookingRepository.get(id)`,
  `list()`, `create(input)`, `update(id, patch)`, and `remove(id)`.
- A third-party API of the definition has a server-only client in
  `@/shared/api/<api>`, for example `holidaysClient()`, which reads the
  base URL and the secret from the environment. Call it in an operation
  or in a new server action (`"use server"`), never in a client
  component. An error status throws `ApiError` of `@/shared/api/third-party`.
  A file of a multipart form is a `Blob` (a `File` gives its name), a
  text answer is a `string`, and a binary answer is a `Blob`. With
  OAuth 2.0, the client gets and renews its tokens itself.
- The components are React client components. Load data with
  `<entity>Api` of `@/entities/<entity>` (for example
  `bookingApi.list()`), which calls the server actions, and with
  `useResource` of `@/shared/lib/use-resource`.
- `<entity>Api.list(query)` gives `{ items, total, page, pageSize }`.
  Without `page` in the query, `items` has all records. The query can
  have `filters`, `sort`, and `search`. `<entity>Api.subscribe(listener)`
  calls the listener after each change of the records, and gives a
  function that stops it.
- `useResource(key, load, subscribe)` gives `{ status: "loading" }`,
  `{ status: "error", error }`, or `{ status: "success", data }`, with
  `reload()`. It calls `load` again when `subscribe` reports a change.
  The generated dashboard `src/widgets/<dashboard>/ui/<dashboard>-dashboard.tsx`
  is an example: it loads the records of each entity, and subscribes to
  their changes.
- The UI components of shadcn/ui are in `@/shared/ui/`.
- The generated views show their states with `ViewLoading`,
  `ViewMessage`, and `RetryButton` of `@/shared/ui/view-state`, for
  example `<ViewLoading indicator="skeleton" shape="widget" />`
  (`indicator` and `shape` are required). Use them for the same look.
- Test: `pnpm install`, `pnpm lint`, `pnpm typecheck`, and
  `pnpm build`. The app has no unit tests and no `test` script. Run it
  with `pnpm dev` (see the README of the app for the database).

| A custom dashboard widget (`kind: custom`)                         | `src/widgets/<dashboard>/ui/<widget>-widget.ext.tsx`      | Nothing. Load the data in the component.                    |

| A custom action (`kind: custom`)                                   | `src/features/<owner>-actions/model/<action>-action.ext.ts` | As in the Next.js app.                                    |
| A third-party API with a secret (`security`) or a cookie parameter | `src/shared/api/<api>/client.ext.ts`                      | Nothing: a browser app cannot keep the secret, or set a cookie for another site. Set `expose: true` on the API, and run `appgen generate` again: the React app then gets a client, and the gap goes away. Or call the API in a custom operation of the FastAPI app (`apis: [<api>]`), and set `x-react-data: api`. Then change the kind of the traces from `gap` to `manual`. |
| A view of API data of an API with a secret or a cookie parameter (`source`) | `src/widgets/<view>/ui/<view>-view.ext.tsx`      | `route` (the path parameters of the page) if the view has a `$route` parameter. Set `expose: true` on the API, and run `appgen generate` again: the gap goes away. With `x-react-data: api` in `app`, the view then calls the FastAPI app. |

- The app uses mock data in the browser. Read and change the data with
  `<entity>Api` of `@/entities/<entity>`, for example
  `bookingApi.update(record.id, { status: "cancelled" })`. Load data in
  a component with `useResource` of `@/shared/lib/use-resource`.
- `list`, `subscribe`, `useResource`, and the view states work as in
  the Next.js app.
- A third-party API without a secret and without a cookie parameter has a client in `@/shared/api/<api>`,
  for example `holidaysClient()`. With mock data, it gives the example
  answers of the OpenAPI document and sends no request. With
  `x-react-data: api`, the browser calls the API at the base URL of the
  build variable `VITE_<base_url_env>`. An error status throws `ApiError`
  of `@/shared/api/third-party`.
- An API with `expose: true` has a client too, also with a secret. With
  `x-react-data: api`, the client calls the endpoints of the FastAPI app
  (`/apis/<api>/<operation>`), which call the API with the secret.
- With `x-react-data: api` in `app`, the app uses the FastAPI app of the
  same definition. Then a custom operation calls its endpoint, and has
  no extension file: fill the gap in the FastAPI app. `<entity>Api.list`
  takes only the filters `eq` and `in` and the sort that the list
  endpoint takes, and no search. `<entity>Api.page({ params, sort,
  page, pageSize })` loads one page with the parameters of the API.
- Test: `pnpm install`, `pnpm lint`, `pnpm typecheck`, and
  `pnpm build`. The app has no unit tests and no `test` script. Run it
  with `pnpm dev`.

## FastAPI

| Extension file                                  | Kind                     | The generated code gives                                     |
| ----------------------------------------------- | ------------------------ | ------------------------------------------------------------ |
| `app/features/<slice>/<operation>_ext.py`       | A gap: a custom operation. | `session` (an `AsyncSession`), `record` (the model of the entity), `params` (a Pydantic model) if the operation has `params`, and a client for each API in `apis` of the operation, for example `holidays: HolidaysClient`. Return the record of `returns`. The endpoint commits the session after the function. |
| `app/core/messages_ext.py`                      | A gap: the delivery of the messages of the sign-in (`auth.password_reset`, `auth.sign_up.verify_email`). | `deliver_message(settings, message)`: send the message to `message.to`, for example by email. The generated `Message` has the `kind` (`password-reset` or `email-verification`), the `user`, the `subject`, the `text` (in the language of the request, with the link), and the `link`. The stub writes the link to the log with `ENVIRONMENT=development`, and else raises `NotImplementedError` (the endpoint gives 501). For plain emails, select `auth.delivery: smtp` in the definition instead: the app then sends them by SMTP and has no such file. |
| `app/features/<slice>/validation_ext.py`        | An optional hook, not a gap (`@trace:manual`). | `validate(session, record, *, created)`: the create and update endpoints call it. Raise `ProblemError(422, "<reason>")` of `app.core.errors` to reject the record. By default, it accepts all records. |
| `app/extensions/routers_ext.py`                 | An optional hook, not a gap (`@trace:manual app`). | `ROUTERS`: a list of `APIRouter`s. The app includes each one after the generated routers, with the middleware of the app (the CORS, the rate limit, and the log). Add a router for an endpoint that the definition does not describe, for example a collect endpoint for a tracking script. By default, the list is empty. |
| `migrations/versions/0001_schema.py`            | The first migration, not a gap (`@trace:manual app`). | Alembic runs it. appgen writes it once and never changes it. |

- `app/features/<slice>/repository.py` has `get(session, id)`,
  `add(session, data)` (without a commit), `create(session, data)`,
  `update(session, record, data)`, and `delete(session, record)`. The
  models are in `app/features/<slice>/models.py`, and the schemas in
  `schemas.py`.
- Raise `ProblemError` of `app.core.errors` for an error response, for
  example `ProblemError(409, "The booking is cancelled already.")`.
- A client of a third-party API is in `app/integrations/<api>/client.py`,
  with one async method for each operation of the API in the
  definition, and the Pydantic models in `models.py`. An error status
  raises `ApiError` of `app.integrations.http`. A file of a multipart
  form is an `ApiFile` (`name`, `content` in bytes, and `content_type`)
  of `app.integrations.http`, a text answer is a `str`, and a binary
  answer is `bytes`. With OAuth 2.0, the client gets and renews its
  tokens itself. The generated tests give the operation a client with a
  mock transport (`tests/integrations/mocks.py`), which answers with the
  examples of the OpenAPI document.
- With `translations`, translate the message with `t` of `app.core.i18n`,
  for example `ProblemError(409, t("The booking is cancelled already."))`,
  and add the message as a key of each language. The response is in the
  language of `Accept-Language`.
- The generated test of a custom operation accepts the status 501 of the
  stub and the result of the logic. Write the tests of your logic in a
  new file, for example `tests/features/<slice>/test_<operation>_logic.py`.
- The factories of `tests/factories.py` (`make_<entity>(session, **values)`)
  give a value to each field, also to the optional fields, and the
  values change with each call. In a test of your logic, give each value
  that the test needs, for example
  `make_task(session, status="todo", completed_at=None)`.
- After a change to the definition that changes the database, make a
  migration: `uv run alembic revision --autogenerate -m "<change>"`.
  It needs a database with the migrations that exist (see "Database
  changes" in [change-definition.md](change-definition.md)).
- Test: `uv sync`, `uv run ruff check`, `uv run ruff format --check`,
  `uv run pyright`, and `uv run pytest`.
- By default, `uv run pytest` starts Postgres with Testcontainers, so
  Docker must run. Without Docker, use SQLite:
  `TEST_DATABASE_URL=sqlite+aiosqlite:///./test.db uv run pytest`.
  Do not skip the tests of the database.
