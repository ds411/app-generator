# Writing a binding

A binding is a target stack: it turns an app definition into the code of
one kind of app. appgen has three bindings for apps (`nextjs`, `react`,
and `fastapi`) and one test binding (`minimal`). This page tells a
maintainer how to write a new binding. The binding contract is in
`src/appgen/gen/binding.py`, and the generator in
`src/appgen/gen/generator.py`.

## How the generator works

`appgen generate <definition> -b <binding> -o <folder>` does these
steps:

1. It loads and validates the definition. If it is not valid, it stops
   and writes no file.
2. It lists the elements of the definition, each with its ID and its
   kind (`entity`, `field`, `page`, `table_view`, and so on).
3. It renders each output rule of the binding with Jinja2. A rule
   renders once, or once for each element of a kind.
4. It makes a gap for each element of a kind that the binding does not
   cover, and renders the gap rule of the binding for it.
5. It writes the files and the manifest `.appgen/manifest.json`. It
   deletes the generated files of the last run that no rule writes any
   more, and it never changes an extension file.

The output is deterministic: the same definition and the same generator
version give the same files, byte for byte. A missing template value
stops the run.

## A first binding

The test binding `minimal` is the smallest example
(`src/appgen/bindings/minimal/`):

```python
from pathlib import Path

from appgen.gen.binding import Binding, Output

BINDING = Binding(
    name="minimal",
    description="A minimal binding that writes an index and one Markdown file for each entity.",
    template_dir=Path(__file__).parent / "templates",
    outputs=(
        Output(template="entity.md.j2", path="entities/{{ name }}.md", for_each="entity"),
        Output(template="index.md.j2", path="index.md"),
        Output(template="app.json.j2", path="app.json"),
    ),
    covers=frozenset({"app", "entity", "field"}),
    gap_rule=Output(template="gap.md.j2", path="gaps/{{ element_id }}.md"),
)
```

`templates/entity.md.j2`:

```jinja
{{ trace_header(element_id) }}
# Entity {{ name }} of {{ app.name }}

{% for field_name, field in element.fields.items() %}
- {{ field_name }}: {{ field.type }} {{ trace(field.id) }}
{% endfor %}
```

The output for the entity `Task`:

```md
<!-- Generated by appgen. Do not edit: change the app definition instead. -->
<!-- @trace entities.Task file -->
# Entity Task of project-tracker

- title: string <!-- @trace entities.Task.fields.title -->
```

## The binding contract

| Field                  | Content                                                                |
| ---------------------- | ---------------------------------------------------------------------- |
| `name`                 | The name for `--binding`, for example `nextjs`.                         |
| `description`          | One line of text.                                                      |
| `template_dir`         | The folder of the Jinja2 templates.                                    |
| `outputs`              | The output rules (see below).                                          |
| `covers`               | The element kinds that the binding generates code for.                 |
| `excludes`             | The element kinds out of the scope of the binding, for example `page` and `ui` for a back end. |
| `gap_rule`             | An output rule for the extension file of each gap element.             |
| `stub_markers`         | The text that the stubs of the extension files contain. Default: `TODO(appgen)`. See [traces.md](traces.md#generation-gaps). |
| `shared_template_dirs` | More template folders, after `template_dir`.                           |
| `context`              | A function of the definition that returns more template values.        |
| `filters`              | More Jinja2 filters.                                                   |
| `helpers`              | Python functions that the templates call, for example `ts_type(field)`. |
| `extension_keys`       | The `x-` keys that the binding reads, with their schema (see [Extension keys](#extension-keys)). |
| `extension_prefix`     | A prefix that only the keys of the binding have, for example `x-fastapi-`. |
| `finish`               | A function of the path, the content, and the definition that changes each rendered file, for example to add an import. |
| `warnings`             | A function of the definition that returns warnings with hints, for example for a part that the binding generates less code for. `appgen generate` prints them. |

`context`, `filters`, `helpers`, `finish`, and `warnings` must be deterministic: they must not
read a clock, random values, or files. `context` cannot replace a value
of the generator.

## Output rules

An `Output` maps a template to a file:

| Field       | Content                                                                 |
| ----------- | ----------------------------------------------------------------------- |
| `template`  | The template name, relative to the template folders.                    |
| `path`      | The output path, a Jinja2 template, for example `src/entities/{{ name \| kebab }}/index.ts`. |
| `for_each`  | An element kind: the rule renders once for each element of the kind.    |
| `when`      | A Jinja2 expression. If it is false, the rule writes no file. With `for_each`, it gets the context of each element. |
| `extension` | True for an extension file (see below).                                 |

Examples from the bindings:

```python
Output(template="app/main.py.j2", path="app/main.py")
Output(
    template="src/features/operation/api/operation.ext.ts.j2",
    path="src/features/{{ name | kebab }}/api/{{ name | kebab }}.ext.ts",
    for_each="operation",
    when="element.kind == 'custom'",
    extension=True,
)
```

Two rules cannot write the same path.

## Templates

Each template gets these values:

| Value          | Content                                                          |
| -------------- | ---------------------------------------------------------------- |
| `definition`   | The whole definition (`AppDefinition`, Pydantic models).          |
| `app`          | `definition.app`.                                                |
| `binding`      | `name`, and `covers` as a sorted list.                           |
| `tokens`       | The resolved design tokens: a flat list sorted by path, with the light and the dark value of each token and its element ID. |
| `element`, `element_id`, `element_kind`, `name` | For a rule with `for_each`: the element. |
| `output_path`, `output_kind` | The file that the template writes, and its kind.    |

The naming filters convert names to the conventions of a language:
`camel`, `pascal`, `kebab`, `snake`, and `constant` (see
`src/appgen/gen/naming.py`), for example `{{ name | pascal }}`.

The kind of an element is the class name of its model in snake case,
for example `entity`, `menu_item`, or `table_view`. A `Field` in
`params` has the kind `param`.

## Traces in templates

Each generated file that can hold comments must have a trace, or the
run stops. Two helpers write traces in the comment syntax of the output
file ([traces.md](traces.md)):

- `trace_header(id, ...)` writes the header of the file: the notice
  "Generated by appgen" (or "Created by appgen once" for an extension
  file) and a file trace for each ID.
- `trace(id, scope=None, kind=None, jsx=False)` writes one trace, for
  example at the end of a line. `jsx=True` writes `{/* ... */}` for a
  JSX child.

Both helpers stop the run for an ID that is not an element. The kind of
a trace is `generated` in a generated file and `gap` in an extension
file.

A trace covers only its own element: a trace to an entity does not
cover its fields. Write a trace for each element that the template
renders. For a file without comments (for example JSON), the manifest
records the traces.

## Coverage, gaps, and scope

Each element kind of the definition is in one of three groups for a
binding:

- **Covered** (`covers`): the templates render the elements and write
  their traces.
- **Excluded** (`excludes`): out of the scope of the binding by design.
  The generator makes no gap for these elements, or for the elements
  under them, and `appgen check` does not count them. The FastAPI
  binding excludes `page` and `ui`, but it reads the stat, chart, and
  list widgets of the dashboards for their endpoints: their traces do
  not count in its coverage. The React binding excludes the
  rules of the entities (`entity_compare_rule`, `entity_unique_rule`,
  and `entity_overlap_rule`) and the webhooks (`webhook`), because it
  has no back end.
- **Gaps**: all other kinds. The generator renders the `gap_rule` for
  each element, an extension file with a gap trace and a
  `TODO(appgen):` comment. Without a gap rule, the gaps are only listed.
  For example, a binding that does not cover the webhooks gives each
  webhook the file `src/gaps/webhooks.<name>.ext.ts`.

A binding must declare each kind that its templates render in
`covers`, else the generator makes gap files for elements that the app
already has. `tests/test_end_to_end.py` checks that each app of the
project tracker has no uncovered elements, and that its open gaps are
the stubs of the custom elements.

## Extension keys

An app author gives a binding more data with extension keys (`x-...`,
ADR 0002). The DSL does not check them, so a binding declares the keys
that it reads in `extension_keys`. Each `ExtensionKey` has:

| Field         | Content                                                              |
| ------------- | -------------------------------------------------------------------- |
| `name`        | The key, for example `x-fastapi-embed`.                              |
| `kinds`       | The element kinds that can have the key, for example `relation`.     |
| `type`        | The type of the value, as a Pydantic type, for example `bool` or `Annotated[int, Field(ge=1)]`. |
| `description` | What the key does. The error messages show it as the hint.           |

`appgen validate` checks the keys of all bindings, or of the bindings
that `--binding` gives. `appgen generate` checks the keys of its
binding, and writes no file if a key is wrong. The check reports, with
the file and the line:

- A declared key on an element of another kind (`invalid-option`).
- A value that does not match the type (`invalid-value`).
- An unknown key with the `extension_prefix` of a binding in use, or an
  unknown key that is close to a declared key, for example
  `x-mock-cont` (`unknown-key`).

The keys of a binding that is not in use give no error. Other unknown
`x-` keys give no error either, so an app author can keep notes in them.

```python
ExtensionKey(
    name="x-fastapi-embed",
    kinds=frozenset({"relation"}),
    type=bool,
    description="True: the read schema embeds the related record as an object.",
)
```

The keys of the bindings of this repository:

| Binding   | Key               | Element kinds    | Value                         |
| --------- | ----------------- | ---------------- | ----------------------------- |
| `fastapi` | `x-fastapi-embed` | `relation`       | A boolean.                    |
| `fastapi` | `x-example`       | `field`, `param` | A JSON value: a valid sample for the tests. |
| `fastapi` | `x-fastapi-path`  | `entity`         | The URL prefix of the router, for example `/meeting-rooms`. |
| `fastapi` | `x-fastapi-table` | `entity`, `relation` | The table name of the entity, or the join table of a `many_to_many` relation. |
| `fastapi` | `x-fastapi-column` | `relation`      | The foreign key column of a `many_to_one` or owning `one_to_one` relation. |
| `fastapi` | `x-fastapi-rate-limit-store` | `app` | `memory` (default) or `redis`: where the rate limit counts the requests. |
| `fastapi` | `x-fastapi-deploy` | `app` | `kubernetes` (default), `knative`, or a list of both: the folders in `deploy/`. |
| `fastapi` | `x-fastapi-search` | `app` | `like` (default) or `fulltext`: the search of `q` in the list endpoints. |
| `nextjs`  | `x-nextjs-rate-limit-store` | `app` | `memory` (default) or `redis`: where the rate limit counts the requests. |
| `nextjs`  | `x-nextjs-deploy` | `app`            | `kubernetes` (default), `knative`, or a list of both: the folders in `deploy/`. |
| `react`   | `x-mock-count`    | `entity`         | An integer, 1 or more.        |
| `react`   | `x-react-data`    | `app`            | `mock` (default) or `api`.    |

### The rate limit and the deployment files

The FastAPI app and the Next.js app have the same production settings
([ADR 0013](adr/0013-fastapi-production.md)):

```yaml
app:
  name: project-tracker
  title: Project Tracker
  x-nextjs-rate-limit-store: redis
  x-nextjs-deploy: [kubernetes, knative]
```

- `RATE_LIMIT_PER_MINUTE` sets the requests that each client address
  can send in each minute (0, the default, sets no limit). Over the
  limit, the app gives 429 with `Retry-After` and a message in the
  language of the request. `/health` has no limit. The FastAPI app counts
  in a middleware. The Next.js app counts in `proxy.ts`, so the limit
  applies to the pages, the server actions, and the route handlers, but
  not to the static files.
- With the store `redis`, `RATE_LIMIT_STORE_URL` selects Redis, and all
  replicas share one limit. When Redis is not available, a request
  passes and the app logs a warning, or gets 503 with
  `RATE_LIMIT_FAIL_CLOSED=true`.
- The client address of the Next.js app comes from `X-Forwarded-For`,
  because the proxy of Next.js does not get the address of the
  connection. `RATE_LIMIT_TRUSTED_HOPS` (default 1) is the number of
  addresses that the proxies in front of the app add to the end of the
  header. The app does not use the addresses that the client sends.
- Each deployment target is a folder in `deploy/`: `kubernetes` (a
  Deployment, a Service, a ConfigMap, an example Secret, and a Job for
  the migrations, with Kustomize) and `knative` (a Knative Service that
  Google Cloud Run accepts too, and a Job for the migrations). The probes
  use `/health`, which checks the database. The Job of the Next.js app
  runs `node migrate.mjs`: the migrations of Drizzle, in a script that
  the image bundles with esbuild.
- `scripts/check-fastapi.sh` and `scripts/check-nextjs.sh` start two
  processes of the app with Redis, and check that they share the limit
  (`scripts/check_shared_rate_limit.py`). They also validate the files of
  each target against their JSON schemas, without a cluster
  (`scripts/check_deploy_files.py`).

### The React app with the FastAPI app

With `x-react-data: api` in the `app` section, the React app uses the
REST API of the FastAPI app of the same definition, and has no mock
data ([ADR 0014](adr/0014-react-api-client.md)):

```yaml
app:
  name: project-tracker
  title: Project Tracker
  x-react-data: api
```

- `src/shared/api/http.ts` sends the requests to `VITE_API_URL`
  (default `http://localhost:8000`), and `http-store.ts` implements the
  same `EntityApi` interface as the mock store. It maps the JSON names
  of the API (`due_date`, `owner_id`) to the keys of the TypeScript
  types (`dueDate`, `ownerId`).
- The paths, the methods, and the JSON names come from the model of the
  FastAPI binding, which also makes the OpenAPI document of the API.
  `scripts/check-react-api.sh` starts both apps, checks each endpoint of
  the client in the OpenAPI document, and opens the project table with
  more projects than one page: each page must load with one request,
  and the search, the sort, and the tabs of a project must load from
  the API. It also counts the requests of the large lists: no page may
  load all records of an entity. The pre-push hook runs it.
- A table or a card list sends its filters, its search, its sort, and
  its page to the list endpoint (`HttpStore.page`), and loads one page.
  A tab of a detail view adds the foreign key of its relation, or `id`
  (the IDs of a `many_to_many` relation). `applyQuery` runs only with
  mock data.
- A view loads the related records that it shows for its page by ID
  (`HttpStore.byIds` and `loadRelated`): one request for each related
  entity, in stages for the related records of related records. A
  detail view does the same for its record.
- A relation field of a form, and a select filter of a relation, search
  their options on the server: the first 20 records in the order of the
  display field, and `q` with the text of the search. Each entity slice
  exports its option source, for example `personOptions`. A `select` or
  a `radio` widget of a relation is a search box in this mode.
- A board loads one page for each column (the query parameter of its
  group field), shows the counts of the server, and has "Show more" for
  each column. A calendar loads only the records of the shown days (the
  date ranges of its start field, and of a required end field).
- A dashboard calls one endpoint for each stat and chart widget, and
  for each list widget: `GET /dashboards/<dashboard>/<widget>`, from the
  FastAPI app. The database computes the values, so the browser gets no
  records for a stat or a chart. A list widget gets only its first
  records, in the order of its sort. A chart of a relation shows the
  groups that have records, with the labels of their records.
- A custom operation calls its endpoint: the FastAPI app runs the
  logic, so the React app has no extension file for it.
- A query ([ADR 0045](adr/0045-queries.md)) calls its endpoint
  `GET /<entity path>/<query>` with the params and the page, and the
  FastAPI app runs the logic and the record rules. The React app has no
  extension file for it.
- With `auth`, the sign-in uses `POST /auth/sign-in`, and each request
  sends the bearer token.
- With `translations`, each request sends the locale of the selected
  language in `Accept-Language`, so the messages of the API are in that
  language. `scripts/check-react-api.sh` opens the page in the second
  language, and checks the header of each request.
- The FastAPI app must allow the origin of the React app (`CORS_ORIGINS`).
- The browser calls each third-party API without a secret and without a
  cookie parameter at the base URL of the build variable
  `VITE_<base_url_env>`, for example `VITE_HOLIDAYS_API_URL`. The API
  must allow the origin of the app. With mock data, the client gives the
  example answers of the OpenAPI document instead.
- The client of an exposed API (`expose: true`) calls the endpoints of
  the FastAPI app (`/apis/<api>/<operation>`), with the bearer token of
  the user, so the secret of the API stays in the FastAPI app.
  `scripts/check-react-api.sh` calls such an endpoint, and checks that
  the FastAPI app sends the API key to the mock server of the APIs.
- A view of API data ([ADR 0022](adr/0022-api-views.md)) calls its
  operation with the client of the API. A view of an API with a secret
  or a cookie parameter, and without `expose`, is a gap: an extension
  file with a stub of the view.

## Extension files

Where the definition asks for hand-written code (a custom operation,
a custom page, a custom widget, and so on), the binding writes two
files ([ADR 0005](adr/0005-generation-gaps.md)):

- A generated file (`*.gen.ts`, `*.gen.tsx`, or `*_gen.py`) with the
  typed signature and the call. It has a `generated` trace.
- An extension file (`*.ext.ts`, `*.ext.tsx`, or `*_ext.py`) with a stub
  that the app developer replaces. It has a `gap` trace and a
  `TODO(appgen):` comment. An output rule with `extension=True` writes
  it.

The generator writes an extension file only if it does not exist, and
never changes or deletes it. The app must build and pass its type check
with the stubs. `appgen.bindings.shared.gaps` has helpers for the gap
files of the front ends (`gap_spec`, `gap_rules()`). The stub of a
custom UI element (a widget, a form widget, or a detail tab) shows its
element ID only in a development build (`process.env.NODE_ENV` in
Next.js, `import.meta.env.DEV` in React). A production build shows the
neutral text "Not available yet.".

The gap of a query ([ADR 0045](adr/0045-queries.md)) returns all rows
of the query in their order. The generated file returns one page of
them, and keeps only the records of `returns` that the record rules let
the user read. A view of a query (`appgen.bindings.shared.query_views`,
the shared template `ui/views/query-view.tsx.j2`) calls the function of
the query in `src/features/<query>` with the params of its filters and
of the page, so the view is the same in the Next.js app and in the
React app.

The examples keep their hand-written code in
`examples/<example>/extensions/<binding>/`, with the paths of the app.
The check scripts copy these files into the app before they generate
it, so that the checks run the real code, for example a custom
operation that calls a third-party API.

A rule with `extension=True` can also write a file that is not a stub
but that belongs to the app after the first run. Give it a manual trace
(`trace("app", scope="file", kind="manual")`), not a gap trace. The
FastAPI binding writes its first migration in this way.

The FastAPI app also has a place for endpoints that the definition does
not describe, for example a collect endpoint for a tracking script or
an LTI launch: `app/extensions/routers_ext.py`. Its list `ROUTERS` is
empty at first, so the file is a hook with a manual trace to `app`, not
a gap (as `validation_ext.py` is). `app/main.py` includes each router
of the list after the generated routers, so the middleware of the app
(the CORS, the rate limit, the log, and the language) applies to them
too. The Next.js app needs no such file: it finds a new route file by
itself. The project tracker example adds a calendar feed of the due
dates in this file, and a test that calls it
(`examples/project-tracker/extensions/fastapi/`).

The logic of a webhook ([ADR 0028](adr/0028-webhooks.md)) is a gap of
the FastAPI app: `app/webhooks/<webhook>/handler_ext.py`. The generated
endpoint in `router.py` checks the signature, reads the event, and
records its ID before it calls the function, so the extension file has
only the logic of the event. The project tracker example adds the
commit message of a code host to a task as a comment in this file
(`examples/project-tracker/extensions/fastapi/app/webhooks/commits/`).
The smoke test signs and sends the event with
`scripts/webhook_sender.py`, and checks that two deliveries of the same
event add one comment.

In the Next.js app, the logic of a webhook is a gap too:
`src/features/<webhook>-webhook/api/<webhook>-webhook.ext.ts`. The
generated route handler `app/<path>/route.ts` calls the function
`receive<Webhook>Webhook` of the slice (`<webhook>-webhook.gen.ts`),
which checks the signature, reads the event with the zod schemas, and
records its ID before it calls `handle<Webhook>` of the extension file.
The project tracker example has the same logic for the commits
(`examples/project-tracker/extensions/nextjs/src/features/commits-webhook/`).
`scripts/webhook_test.py` sends signed events to each webhook of
`tests/fixtures/webhooks.yaml`, with the stubs of the extension files.

A webhook with `format: email` ([ADR 0030](adr/0030-inbound-email.md))
has the same gap, and its function gets the inbound email
(`InboundEmail`). The fixture `tests/fixtures/inbound-email.yaml` has
hand-written logic for both apps in `tests/fixtures/inbound-email/extensions/`:
an email makes a ticket, and a reply counts on the ticket of the email
that it answers. `scripts/inbound_email_test.py` sends emails in the
format of Mailgun, Postmark, and SendGrid to the built apps.

### Connections of the users to the APIs

A custom operation that calls an API with the authorization code flow
([ADR 0033](adr/0033-api-connections.md)) gets the client of the
signed-in user in its extension file, and a job gets the client of the
user of the record. The function calls the client as for another API:
the client reads the access token of the user in the table
`api_connections` (`app/core/connections.py`), and gets a new token when
the token ends. A request raises `NotConnectedError` (409) when the user
has no connection. The fixture `tests/fixtures/api-connections.yaml`
has hand-written logic in `tests/fixtures/api-connections/extensions/`
that counts the events of the calendar of a user.
`scripts/api_connection_test.py` connects a user at the mock OAuth
server of `scripts/mock_api.py`, and checks the calls of the operation,
of the job, and the refresh of a token.

The Next.js app has the same table and token source in
`src/shared/auth/connections.ts`. The extension file of a custom
operation calls `<api>Client()`, which uses the signed-in user, and a
job runs the operation in the name of the user of the record. The
routes `/connections/<api>/start` and `/connections/<api>/callback` run
the flow. The front ends show the page `/connections` with
`ConnectionsPage` of `src/features/connections/`, and a link to it in
the layout. `scripts/connection_ui_test.py` connects, syncs, and
disconnects an account on this page with React, Next.js, and React with
the FastAPI app.

### Schema changes of the FastAPI app

The FastAPI app creates the first migration
(`migrations/versions/0001_schema.py`) once, and a new run keeps all
migrations ([ADR 0009](adr/0009-fastapi-schema-changes.md)). To change
the schema of a database that has data:

1. Change the app definition, and generate the app again into the same
   folder: `uv run appgen generate app.yaml -b fastapi -o <app>`.
2. In the app folder, make the next migration from the changed models:
   `uv run alembic revision --autogenerate -m "<change>"`. Alembic
   compares the models with the database of `DATABASE_URL`.
3. Review the new file in `migrations/versions/`. Edit it for the
   changes that Alembic does not find, for example a rename or a
   changed enum value.
4. Apply it: `uv run alembic upgrade head`. The data stays.

`scripts/check_schema_change.py` runs these steps on a copy of the
project tracker with SQLite, and checks that a record stays. The change
adds a field, and makes a field translatable: the next migration adds
the column of its translations
([ADR 0026](adr/0026-record-translations.md)).

### The full-text search of the FastAPI app

With `x-fastapi-search: fulltext` in the `app` section, the parameter
`q` of the list endpoints is a web search on Postgres: words, a phrase
in quotes, `or`, and `-word` for a word that a record must not have.

```yaml
app:
  name: project-tracker
  title: Project Tracker
  x-fastapi-search: fulltext
```

- The text fields of the entity in its search filters (and its display
  field, if it is a text) make one text search vector
  (`search_vector` in `app/core/search.py`). A GIN index on the vector
  makes the search fast. A field of a related record, for example
  `owner.name`, has its own vector, without an index.
- The text search configuration comes from the default language of
  `translations`, for example `english` for `en` and `german` for `de`,
  else `simple`. A configuration of a language compares the stems of
  the words: `reports` finds `report`. A translatable field keeps the
  value of the default language in its column, so the search compares
  the words of that value ([ADR 0026](adr/0026-record-translations.md)).
- Without a sort, the records come in the order of their rank
  (`ts_rank`). With a sort, the sort decides the order.
- On SQLite, the search stays `LIKE` for each word, and the migrations
  do not create the GIN indexes.
- A new app gets the GIN indexes in its first migration. To add them to
  an app that exists, generate the app again, and make the next
  migration with Alembic on a Postgres database:
  `DATABASE_URL=postgresql+asyncpg://... uv run alembic revision --autogenerate -m "full-text search"`.
  `migrations/env.py` writes each GIN index under a test of the
  dialect, so that the migration also runs on SQLite. On SQLite,
  Alembic does not compare the indexes of an expression.
- The generated tests check the rank, `-word`, a phrase, and `or` on
  Postgres. `scripts/check_full_text_search.py` (in
  `scripts/check-fastapi.sh`) adds the indexes to an app that exists on
  Postgres, and checks that the search of the projects uses its index.

### The events of the FastAPI app

The repository of an entity runs its `events` and the `run` operations
of its transitions ([ADR 0031](adr/0031-events.md)), so that the
generated operations and the custom operations both start them.

- `add` (and so `create`) runs `on_created` after a flush of the new
  record. `update` keeps the values of the watched fields in `before`,
  and runs `on_changed` after a flush: first the operations of the
  transitions of the change, then the operation of `changed` if a field
  of `CHANGED_FIELDS` has a new value. `delete` runs `on_deleted` after
  a flush of the delete.
- Each of these functions imports the extension modules of the
  operations (`<operation>_ext.py`) in its body, because these modules
  can import the repository.
- `run_event` in `app/core/db.py` runs an operation with the key
  `appgen.event` in `session.info`. While the key is there, `commit()`
  only flushes, and `run_event` runs no other operation: the events stop
  after one level. An error leaves the transaction without a commit, so
  the change and the work of the operation roll back.
- The autouse fixture `turn_off_events` of `tests/conftest.py` replaces
  `on_created`, `on_changed`, and `on_deleted` with functions that do
  nothing, so that the generated tests of the other features do not
  depend on the logic of the operations. The mark
  `@pytest.mark.events` keeps the events of all entities, and
  `@pytest.mark.events("Booking")` the events of one entity.
- The generated tests in `tests/features/<slice>/test_events.py` replace
  the operations with fakes, and check each kind of event: the record is
  in the database (or deleted) at the time of the call, a failed
  operation rolls back the change and a change of the operation, a
  change of other fields or no change runs no `changed`, and a change in
  the operation starts no event.

### The live updates of the FastAPI app

The FastAPI app sends the changes of the records of the entities with
`live` as server-sent events ([ADR 0051](adr/0051-live-updates.md)).
`app/core/live.py` has the table `LIVE` of the live entities, the
listeners of the sessions, the broker, and the endpoint `GET /live`.

- `create_app()` makes the broker (`app.state.live`) with
  `LIVE_EVENTS_URL`, and puts it in the `info` of the sessions
  (`BROKER_KEY`). The listeners do nothing in a session without a
  broker. The worker of the jobs makes its own broker only with
  `LIVE_EVENTS_URL`, because its changes go to the streams only through
  Redis.
- `after_flush` keeps the creates, the changes, and the deletes of the
  live records in `session.info` (`PENDING_KEY`). `after_commit` gives
  them to the broker as `Change` values, and `after_rollback` drops
  them.
- With a record rule for the reads of a live entity, `before_flush`
  keeps the audience of each changed or deleted record before its first
  change (`_audience()`: the roles whose conditions the record meets,
  and the users at the end of the owner path), and `after_flush` the
  audience after the change. `Viewer.sees()` compares them with the
  role and the user of the stream.
- `live_viewer()` reads the token without the dependency of the user,
  in a session of its own, so that a stream holds no database
  connection. It gives 401 or 403 for an entity that the client may not
  read. With the sign-in, `POST /live/ticket` gives the signed-in user a
  ticket for 30 seconds (`sign()` of the sessions, with the purpose
  `live`), and `GET /live?ticket=...` takes it instead of the token,
  because `EventSource` cannot send a header.
- The broker gives each stream a `Subscription`: a queue of at most 100
  events. A full queue gives `reset`. With Redis, a task sends the
  changes to the channel `<package>:live`, and another task gives the
  changes of the channel to the subscriptions. When Redis fails, the
  broker logs a warning, and gives the changes to the subscriptions of
  the process until the listener connects again. Then each subscription
  gets `reset`.
- `end_streams_on_exit()` ends the streams at SIGINT and SIGTERM, and
  then calls the signal handler of the server, because the server waits
  for the open requests before it stops.
- The generated tests in `tests/test_live.py` read the stream from the
  ASGI messages of the app, because the HTTP client of the other tests
  gives a response only at its end. They check the events of a create, a
  change, and a delete, a rollback, 401 and 403, the events of the
  record rules, `reset`, the end of the streams, and the broker without
  Redis. `scripts/check_live_events.py` starts two processes with
  Redis, and checks that both streams get the changes of each process
  in less than 2 s.

### The worker of the FastAPI app

The FastAPI app runs the `jobs` of the definition in a worker process
([ADR 0029](adr/0029-jobs.md)): `python -m app.worker`, from the image of
the API. Compose starts it as the service `worker`.

- Each job is a module in `app/jobs/`: its schedule or the field of
  `at` and the offset, the filter of its records (`where`), the runs
  that are due at a time (`due`), and `run`. A job with an entity calls
  its custom operation (`app/features/<slice>/<operation>_ext.py`) on
  each record. A job without an entity calls the function of its
  extension file `app/jobs/<job>_ext.py`, a generation gap.
- `app/core/jobs.py` has the table `job_runs`, the cron schedules, and
  `run_due`: it inserts the row of each run before it starts the run, so
  two workers never start the same run. A worker takes a failed run
  again, or a run whose lock (10 minutes) ended. The work of a run and
  its state `done` are in one transaction. A failed run rolls back, and
  goes into the log of `app.jobs` with the keys `job`, `record_id`, and
  `due`.
- `app/worker.py` runs a pass of all jobs each `JOBS_INTERVAL_SECONDS`
  (60). Each pass looks back over `JOBS_WINDOW_MINUTES` (60) for the
  times that are not done. A failed job does not stop the other jobs.
  The worker stops at SIGTERM or SIGINT after the current pass.
- `GET /health` on `WORKER_PORT` (8001) gives 200 while the passes run,
  and 503 when no pass ends for 3 intervals (at least 5 minutes). The
  liveness probes of the deployment files use it.
- `python -m app.worker --once --now 2026-06-15T12:00:00Z` runs one pass
  at a fixed time.
- The deployment files have a worker: a Deployment with 2 replicas in
  `deploy/kubernetes/worker.yaml`, and a Knative Service with one
  instance and the CPU also between requests (for Cloud Run) in
  `deploy/knative/worker.yaml`.
- The generated tests in `tests/jobs/` run each job with a fixed clock.
  They replace the operation (or the function of the extension file)
  with a fake, and check that each run runs one time, also with two
  workers at the same time, that a record of another time or outside
  the filter does not run, that a change of the date field gives a new
  run, and that a failed run is in the log and runs again.

### The jobs of the Next.js app

The Next.js app has no worker process. It runs each job of the
definition in the route `POST /api/jobs/<job>`
([ADR 0029](adr/0029-jobs.md)), and a scheduler calls the routes.

- Each job is a module in `src/app/jobs/`: its schedule or the offset of
  its date field, the filter of its records (`where`, a Drizzle
  condition), the runs that are due at a time (`due`), and
  `run<Job>(now, windowMs)`. A job with an entity calls its custom
  operation (`src/features/<operation>/api/<operation>.ext.ts`) on each
  record, with the default values of the params. A job without an
  entity calls the function of its extension file
  `src/app/jobs/<job>.ext.ts`, a generation gap.
- `src/shared/lib/jobs.ts` has the cron schedules, `runDue`, and
  `handleJob`. `runDue` inserts the row of each run in the table
  `job_runs` (the same table and keys as in the FastAPI app) before it
  starts the run, so two calls never start the same run. The work of a
  run and its state `done` are in one transaction: `inTransaction()` of
  `@/shared/db` makes `getDb()` return the transaction, so the
  repositories in the operation write in it. A failed run rolls back,
  goes into the log as a JSON line with `job`, `record_id`, and `due`,
  and runs again at the next call while its time is in the window.
- `handleJob` checks the header `Authorization: Bearer <JOBS_SECRET>`
  (else 401), runs the job for the times of the last
  `JOBS_WINDOW_MINUTES` (60), and gives `{ job, now, runs, failed }`,
  with the status 500 when a run failed. With `JOBS_FIXED_CLOCK=true`,
  the parameter `now` sets the time of the call.
- The deployment files have a CronJob (a curl image) for each job with a
  schedule, and one each minute for the jobs with `at`:
  `deploy/kubernetes/jobs.yaml` and `deploy/knative/jobs.yaml`. On Cloud
  Run, Cloud Scheduler calls the routes (the README of the app has the
  commands). Compose starts the service `jobs`, which calls each route
  each minute.
- `scripts/jobs_test.py` calls the route handlers of
  `tests/fixtures/jobs.yaml` with a fixed clock and PGlite, with the
  hand-written operations of `tests/fixtures/jobs-extensions/nextjs/`.

### The events of the Next.js app and of the React app

The repository of each entity in the Next.js app runs its `events` and
the `run` operations of its transitions
([ADR 0031](adr/0031-events.md)), as the FastAPI repository does. The
server actions and the custom operations use the repositories, so both
start the events.

- The options of the repository have `events`: `created`, `changed`
  (with the `keys` of the fields that it watches), `deleted`, and
  `transitions` (the field, the states before, and the state after).
  Each one is a function that imports the extension file of the
  operation (`import()`) when the event runs, because the operation
  imports the repository. This is the one import from the entities
  layer to the features layer, and it happens only when an event runs.
- `create` and `update` run the operations in their transaction, after
  the change, and give the record as the operations leave it. `update`
  runs the operations of the transitions first, then the operation of
  `changed`. With `deleted`, `remove` reads the record, deletes it, and
  runs the operation in one transaction. It deletes the files of the

### The memberships of the Next.js app and of the React app

  throws a `ScopeError` for a record in another scope of the user.

  `requireOperation()` lets the operations of `MEMBER_OPERATIONS` pass,

  of the records of an entity of the scope or of the membership entity.

  the operation, or if a membership gives it on each record of the IDs.
  `canCall(operation)` is true for a create or a list that a membership
  gives in some scope. `memberGives()` asks the data access once for all
  records of one render, and the hook renders the component again when

### The live updates of the Next.js app and of the React app

The front ends load their open views again after the changes of the
records of the entities with `live` ([ADR 0051](adr/0051-live-updates.md)).

- The Next.js app sends the changes as the FastAPI app does.
  `src/shared/db/live.ts` has the table `LIVE` of the live entities,
  the broker (`liveBroker()`, one for each process, also after a hot
  reload), and the audiences of the record rules (`liveAudience()`).
  The repository of a live entity has the option `live`: `create`,
  `update`, `remove`, and the file uploads run in `liveChanges()`, and
  call `noteChange()` in their transactions. `afterCommit()` of
  `src/shared/db/client.ts` gives the changes to the broker after the
  commit of the outer transaction. A change in the operation of an
  event joins the changes of the outer work.
- The route `app/api/live/route.ts` reads the session cookie, and sends
  the events of a `Subscription` of the broker. The stream asks the
  subscription for the next event only when the client reads, and sends
  a comment each 15 seconds without an event. The headers
  `Cache-Control: no-cache, no-transform` and `X-Accel-Buffering: no`
  stop the compression of Next.js and the buffers of the proxies.
  `instrumentation.ts` ends the streams at SIGINT and SIGTERM.
- With `LIVE_EVENTS_URL`, the broker uses `@redis/client`: a publisher
  without the offline queue, and a subscriber of the channel
  `<app name>:live`. The packages are the packages of the shared rate
  limit.
- `src/shared/lib/live.ts` (a shared template) has the client:
  `watchLive()` reads the stream with `EventSource`, and `batched()`
  calls `notifyChange()` once for each entity after 50 ms, or once
  without an entity after `reset`. The component
  `src/app/providers/live-updates.tsx` starts the client. In the
  Next.js app, `notifyChange()` of `@/shared/api` calls the listeners
  of the resources of the views. In the React app, it marks the HTTP
  stores of the entity (`src/shared/api/http-store.ts`) as old, so the
  open views load their data again. The root layout of the Next.js app
  gives the component the key of the signed-in user, so a new user
  opens a new stream.
- With the sign-in, the React app gets a ticket from `POST /live/ticket`
  before each new stream, and opens a new stream after each new access
  token (`subscribeAccessToken()` of `src/shared/api/http.ts`).
- `scripts/live_test.py` runs the server code of the Next.js app of
  `tests/fixtures/record-rules.yaml` with tsx and PGlite: the events of
  each role and user, two brokers with one Redis, a broker without
  Redis, and the end of the streams. The UI test
  `ui-tests/tests/live.spec.ts` changes a task in a second browser, and
  checks that the task board of the first browser shows each change in
  less than 2 s: in the Next.js app, and in the React app with the
  FastAPI app (`scripts/api_client_test.py`).

The Next.js and the React bindings share templates in
`src/appgen/bindings/shared/templates/`: the shadcn/ui components, the
theme, the app shell, the views, the forms, the dashboards, and the
entity types. Python modules next to them (`ui.py`, `views.py`,
`forms.py`, `details.py`, `dashboards.py`) compute the plans that the
templates render. A binding uses them with
`shared_template_dirs=(shared.TEMPLATE_DIR,)`. A template in the folder
of the binding with the same name wins over a shared template.

The shared UI code imports only `@/shared/*`, `@/widgets/*`,
`@/features/*`, and `@/entities/<entity>`. Each front-end binding
writes `@/shared/lib/router` (with `Link`, `useNavigate`, `usePathname`,
and `useParams`) and the entity slices with the same public API, so the
same UI code works with both routers and both data layers.

## Register the binding

Add an entry point in the group `appgen.bindings` in `pyproject.toml`,
and run `uv sync`:

```toml
[project.entry-points."appgen.bindings"]
mybinding = "appgen.bindings.mybinding:BINDING"
```

## Test and check the binding

- Add `tests/test_binding_<name>.py`: generate the example, check the
  important files, check that two runs give the same output, and check
  that `appgen check` finds no invalid traces.
- Add the binding to `BY_DESIGN` in `tests/test_end_to_end.py`, with
  the kinds that it excludes.
- Add `scripts/check-<name>.sh`: generate the example, install, lint,
  type check, build, run the tests of the app, `docker build`,
  `appgen check`, and the smoke test (`scripts/smoke_test.py`). Add the
  binding to the smoke test.
- Add the script and its path patterns to `.githooks/pre-push`.
- Pin the package versions of the generated app in a `versions.py`.
- Describe the binding in the README.

## Checklist

- [ ] Each generated file has a trace header, and each rendered element
      has a trace.
- [ ] `covers` lists all kinds that the templates render, and `excludes`
      lists the kinds out of scope.
- [ ] Hand-written code goes in extension files only.
- [ ] `extension_keys` declares each `x-` key that the binding reads.
- [ ] Two runs give the same output.
- [ ] The generated app builds with the stubs of the extension files.
- [ ] `appgen check` reports no invalid traces, and the expected
      coverage.
- [ ] The app has a Dockerfile, and uses uv (Python) or pnpm (TypeScript).
