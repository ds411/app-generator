# Writing a binding

A binding is a target stack: it turns an app definition into the code of
one kind of app. appgen has three bindings for apps (`nextjs`, `react`,
and `fastapi`) and one test binding (`minimal`). This page tells a
maintainer how to write a new binding. The binding contract is in
`src/appgen/gen/binding.py`, and the generator in
`src/appgen/gen/generator.py`.

## How the generator works

`appgen generate <definition> -b <binding> -o <folder>` does these
steps:

1. It loads and validates the definition. If it is not valid, it stops
   and writes no file.
2. It lists the elements of the definition, each with its ID and its
   kind (`entity`, `field`, `page`, `table_view`, and so on).
3. It renders each output rule of the binding with Jinja2. A rule
   renders once, or once for each element of a kind.
4. It makes a gap for each element of a kind that the binding does not
   cover, and renders the gap rule of the binding for it.
5. It writes the files and the manifest `.appgen/manifest.json`. It
   deletes the generated files of the last run that no rule writes any
   more, and it never changes an extension file.

The output is deterministic: the same definition and the same generator
version give the same files, byte for byte. A missing template value
stops the run.

## A first binding

The test binding `minimal` is the smallest example
(`src/appgen/bindings/minimal/`):

```python
from pathlib import Path

from appgen.gen.binding import Binding, Output

BINDING = Binding(
    name="minimal",
    description="A minimal binding that writes an index and one Markdown file for each entity.",
    template_dir=Path(__file__).parent / "templates",
    outputs=(
        Output(template="entity.md.j2", path="entities/{{ name }}.md", for_each="entity"),
        Output(template="index.md.j2", path="index.md"),
        Output(template="app.json.j2", path="app.json"),
    ),
    covers=frozenset({"app", "entity", "field"}),
    gap_rule=Output(template="gap.md.j2", path="gaps/{{ element_id }}.md"),
)
```

`templates/entity.md.j2`:

```jinja
{{ trace_header(element_id) }}
# Entity {{ name }} of {{ app.name }}

{% for field_name, field in element.fields.items() %}
- {{ field_name }}: {{ field.type }} {{ trace(field.id) }}
{% endfor %}
```

The output for the entity `Task`:

```md
<!-- Generated by appgen. Do not edit: change the app definition instead. -->
<!-- @trace entities.Task file -->
# Entity Task of project-tracker

- title: string <!-- @trace entities.Task.fields.title -->
```

## The binding contract

| Field                  | Content                                                                |
| ---------------------- | ---------------------------------------------------------------------- |
| `name`                 | The name for `--binding`, for example `nextjs`.                         |
| `description`          | One line of text.                                                      |
| `template_dir`         | The folder of the Jinja2 templates.                                    |
| `outputs`              | The output rules (see below).                                          |
| `covers`               | The element kinds that the binding generates code for.                 |
| `excludes`             | The element kinds out of the scope of the binding, for example `page` and `ui` for a back end. |
| `gap_rule`             | An output rule for the extension file of each gap element.             |
| `stub_markers`         | The text that the stubs of the extension files contain. Default: `TODO(appgen)`. See [traces.md](traces.md#generation-gaps). |
| `shared_template_dirs` | More template folders, after `template_dir`.                           |
| `context`              | A function of the definition that returns more template values.        |
| `filters`              | More Jinja2 filters.                                                   |
| `helpers`              | Python functions that the templates call, for example `ts_type(field)`. |
| `extension_keys`       | The `x-` keys that the binding reads, with their schema (see [Extension keys](#extension-keys)). |
| `extension_prefix`     | A prefix that only the keys of the binding have, for example `x-fastapi-`. |
| `finish`               | A function of the path, the content, and the definition that changes each rendered file, for example to add an import. |
| `warnings`             | A function of the definition that returns warnings with hints, for example for a part that the binding generates less code for. `appgen generate` prints them. |

`context`, `filters`, `helpers`, `finish`, and `warnings` must be deterministic: they must not
read a clock, random values, or files. `context` cannot replace a value
of the generator.

## Output rules

An `Output` maps a template to a file:

| Field       | Content                                                                 |
| ----------- | ----------------------------------------------------------------------- |
| `template`  | The template name, relative to the template folders.                    |
| `path`      | The output path, a Jinja2 template, for example `src/entities/{{ name \| kebab }}/index.ts`. |
| `for_each`  | An element kind: the rule renders once for each element of the kind.    |
| `when`      | A Jinja2 expression. If it is false, the rule writes no file. With `for_each`, it gets the context of each element. |
| `extension` | True for an extension file (see below).                                 |

Examples from the bindings:

```python
Output(template="app/main.py.j2", path="app/main.py")
Output(
    template="src/features/operation/api/operation.ext.ts.j2",
    path="src/features/{{ name | kebab }}/api/{{ name | kebab }}.ext.ts",
    for_each="operation",
    when="element.kind == 'custom'",
    extension=True,
)
```

Two rules cannot write the same path.

## Templates

Each template gets these values:

| Value          | Content                                                          |
| -------------- | ---------------------------------------------------------------- |
| `definition`   | The whole definition (`AppDefinition`, Pydantic models).          |
| `app`          | `definition.app`.                                                |
| `binding`      | `name`, and `covers` as a sorted list.                           |
| `tokens`       | The resolved design tokens: a flat list sorted by path, with the light and the dark value of each token and its element ID. |
| `element`, `element_id`, `element_kind`, `name` | For a rule with `for_each`: the element. |
| `output_path`, `output_kind` | The file that the template writes, and its kind.    |

The naming filters convert names to the conventions of a language:
`camel`, `pascal`, `kebab`, `snake`, and `constant` (see
`src/appgen/gen/naming.py`), for example `{{ name | pascal }}`.

The kind of an element is the class name of its model in snake case,
for example `entity`, `menu_item`, or `table_view`. A `Field` in
`params` has the kind `param`.

## Traces in templates

Each generated file that can hold comments must have a trace, or the
run stops. Two helpers write traces in the comment syntax of the output
file ([traces.md](traces.md)):

- `trace_header(id, ...)` writes the header of the file: the notice
  "Generated by appgen" (or "Created by appgen once" for an extension
  file) and a file trace for each ID.
- `trace(id, scope=None, kind=None, jsx=False)` writes one trace, for
  example at the end of a line. `jsx=True` writes `{/* ... */}` for a
  JSX child.

Both helpers stop the run for an ID that is not an element. The kind of
a trace is `generated` in a generated file and `gap` in an extension
file.

A trace covers only its own element: a trace to an entity does not
cover its fields. Write a trace for each element that the template
renders. For a file without comments (for example JSON), the manifest
records the traces.

## Coverage, gaps, and scope

Each element kind of the definition is in one of three groups for a
binding:

- **Covered** (`covers`): the templates render the elements and write
  their traces.
- **Excluded** (`excludes`): out of the scope of the binding by design.
  The generator makes no gap for these elements, or for the elements
  under them, and `appgen check` does not count them. The FastAPI
  binding excludes `page` and `ui`, but it reads the stat, chart, and
  list widgets of the dashboards for their endpoints: their traces do
  not count in its coverage. The React binding excludes the
  rules of the entities (`entity_compare_rule`, `entity_unique_rule`,
  and `entity_overlap_rule`), because it has no back end.
- **Gaps**: all other kinds. The generator renders the `gap_rule` for
  each element, an extension file with a gap trace and a
  `TODO(appgen):` comment. Without a gap rule, the gaps are only listed.

A binding must declare each kind that its templates render in
`covers`, else the generator makes gap files for elements that the app
already has. `tests/test_end_to_end.py` checks that each app of the
project tracker has no uncovered elements, and that its open gaps are
the stubs of the custom elements.

## Extension keys

An app author gives a binding more data with extension keys (`x-...`,
ADR 0002). The DSL does not check them, so a binding declares the keys
that it reads in `extension_keys`. Each `ExtensionKey` has:

| Field         | Content                                                              |
| ------------- | -------------------------------------------------------------------- |
| `name`        | The key, for example `x-fastapi-embed`.                              |
| `kinds`       | The element kinds that can have the key, for example `relation`.     |
| `type`        | The type of the value, as a Pydantic type, for example `bool` or `Annotated[int, Field(ge=1)]`. |
| `description` | What the key does. The error messages show it as the hint.           |

`appgen validate` checks the keys of all bindings, or of the bindings
that `--binding` gives. `appgen generate` checks the keys of its
binding, and writes no file if a key is wrong. The check reports, with
the file and the line:

- A declared key on an element of another kind (`invalid-option`).
- A value that does not match the type (`invalid-value`).
- An unknown key with the `extension_prefix` of a binding in use, or an
  unknown key that is close to a declared key, for example
  `x-mock-cont` (`unknown-key`).

The keys of a binding that is not in use give no error. Other unknown
`x-` keys give no error either, so an app author can keep notes in them.

```python
ExtensionKey(
    name="x-fastapi-embed",
    kinds=frozenset({"relation"}),
    type=bool,
    description="True: the read schema embeds the related record as an object.",
)
```

The keys of the bindings of this repository:

| Binding   | Key               | Element kinds    | Value                         |
| --------- | ----------------- | ---------------- | ----------------------------- |
| `fastapi` | `x-fastapi-embed` | `relation`       | A boolean.                    |
| `fastapi` | `x-example`       | `field`, `param` | A JSON value: a valid sample for the tests. |
| `fastapi` | `x-fastapi-path`  | `entity`         | The URL prefix of the router, for example `/meeting-rooms`. |
| `fastapi` | `x-fastapi-table` | `entity`, `relation` | The table name of the entity, or the join table of a `many_to_many` relation. |
| `fastapi` | `x-fastapi-column` | `relation`      | The foreign key column of a `many_to_one` or owning `one_to_one` relation. |
| `fastapi` | `x-fastapi-rate-limit-store` | `app` | `memory` (default) or `redis`: where the rate limit counts the requests. |
| `fastapi` | `x-fastapi-deploy` | `app` | `kubernetes` (default), `knative`, or a list of both: the folders in `deploy/`. |
| `nextjs`  | `x-nextjs-rate-limit-store` | `app` | `memory` (default) or `redis`: where the rate limit counts the requests. |
| `nextjs`  | `x-nextjs-deploy` | `app`            | `kubernetes` (default), `knative`, or a list of both: the folders in `deploy/`. |
| `react`   | `x-mock-count`    | `entity`         | An integer, 1 or more.        |
| `react`   | `x-react-data`    | `app`            | `mock` (default) or `api`.    |

### The rate limit and the deployment files

The FastAPI app and the Next.js app have the same production settings
([ADR 0013](adr/0013-fastapi-production.md)):

```yaml
app:
  name: project-tracker
  title: Project Tracker
  x-nextjs-rate-limit-store: redis
  x-nextjs-deploy: [kubernetes, knative]
```

- `RATE_LIMIT_PER_MINUTE` sets the requests that each client address
  can send in each minute (0, the default, sets no limit). Over the
  limit, the app gives 429 with `Retry-After` and a message in the
  language of the request. `/health` has no limit. The FastAPI app counts
  in a middleware. The Next.js app counts in `proxy.ts`, so the limit
  applies to the pages, the server actions, and the route handlers, but
  not to the static files.
- With the store `redis`, `RATE_LIMIT_STORE_URL` selects Redis, and all
  replicas share one limit. When Redis is not available, a request
  passes and the app logs a warning, or gets 503 with
  `RATE_LIMIT_FAIL_CLOSED=true`.
- The client address of the Next.js app comes from `X-Forwarded-For`,
  because the proxy of Next.js does not get the address of the
  connection. `RATE_LIMIT_TRUSTED_HOPS` (default 1) is the number of
  addresses that the proxies in front of the app add to the end of the
  header. The app does not use the addresses that the client sends.
- Each deployment target is a folder in `deploy/`: `kubernetes` (a
  Deployment, a Service, a ConfigMap, an example Secret, and a Job for
  the migrations, with Kustomize) and `knative` (a Knative Service that
  Google Cloud Run accepts too, and a Job for the migrations). The probes
  use `/health`, which checks the database. The Job of the Next.js app
  runs `node migrate.mjs`: the migrations of Drizzle, in a script that
  the image bundles with esbuild.
- `scripts/check-fastapi.sh` and `scripts/check-nextjs.sh` start two
  processes of the app with Redis, and check that they share the limit
  (`scripts/check_shared_rate_limit.py`). They also validate the files of
  each target against their JSON schemas, without a cluster
  (`scripts/check_deploy_files.py`).

### The React app with the FastAPI app

With `x-react-data: api` in the `app` section, the React app uses the
REST API of the FastAPI app of the same definition, and has no mock
data ([ADR 0014](adr/0014-react-api-client.md)):

```yaml
app:
  name: project-tracker
  title: Project Tracker
  x-react-data: api
```

- `src/shared/api/http.ts` sends the requests to `VITE_API_URL`
  (default `http://localhost:8000`), and `http-store.ts` implements the
  same `EntityApi` interface as the mock store. It maps the JSON names
  of the API (`due_date`, `owner_id`) to the keys of the TypeScript
  types (`dueDate`, `ownerId`).
- The paths, the methods, and the JSON names come from the model of the
  FastAPI binding, which also makes the OpenAPI document of the API.
  `scripts/check-react-api.sh` starts both apps, checks each endpoint of
  the client in the OpenAPI document, and opens the project table with
  more projects than one page: each page must load with one request,
  and the search, the sort, and the tabs of a project must load from
  the API. It also counts the requests of the large lists: no page may
  load all records of an entity. The pre-push hook runs it.
- A table or a card list sends its filters, its search, its sort, and
  its page to the list endpoint (`HttpStore.page`), and loads one page.
  A tab of a detail view adds the foreign key of its relation, or `id`
  (the IDs of a `many_to_many` relation). `applyQuery` runs only with
  mock data.
- A view loads the related records that it shows for its page by ID
  (`HttpStore.byIds` and `loadRelated`): one request for each related
  entity, in stages for the related records of related records. A
  detail view does the same for its record.
- A relation field of a form, and a select filter of a relation, search
  their options on the server: the first 20 records in the order of the
  display field, and `q` with the text of the search. Each entity slice
  exports its option source, for example `personOptions`. A `select` or
  a `radio` widget of a relation is a search box in this mode.
- A board loads one page for each column (the query parameter of its
  group field), shows the counts of the server, and has "Show more" for
  each column. A calendar loads only the records of the shown days (the
  date ranges of its start field, and of a required end field).
- A dashboard calls one endpoint for each stat and chart widget, and
  for each list widget: `GET /dashboards/<dashboard>/<widget>`, from the
  FastAPI app. The database computes the values, so the browser gets no
  records for a stat or a chart. A list widget gets only its first
  records, in the order of its sort. A chart of a relation shows the
  groups that have records, with the labels of their records.
- A custom operation calls its endpoint: the FastAPI app runs the
  logic, so the React app has no extension file for it.
- With `auth`, the sign-in uses `POST /auth/sign-in`, and each request
  sends the bearer token.
- With `translations`, each request sends the locale of the selected
  language in `Accept-Language`, so the messages of the API are in that
  language. `scripts/check-react-api.sh` opens the page in the second
  language, and checks the header of each request.
- The FastAPI app must allow the origin of the React app (`CORS_ORIGINS`).
- The browser calls each third-party API without a secret and without a
  cookie parameter at the base URL of the build variable
  `VITE_<base_url_env>`, for example `VITE_HOLIDAYS_API_URL`. The API
  must allow the origin of the app. With mock data, the client gives the
  example answers of the OpenAPI document instead.
- The client of an exposed API (`expose: true`) calls the endpoints of
  the FastAPI app (`/apis/<api>/<operation>`), with the bearer token of
  the user, so the secret of the API stays in the FastAPI app.
  `scripts/check-react-api.sh` calls such an endpoint, and checks that
  the FastAPI app sends the API key to the mock server of the APIs.
- A view of API data ([ADR 0022](adr/0022-api-views.md)) calls its
  operation with the client of the API. A view of an API with a secret
  or a cookie parameter, and without `expose`, is a gap: an extension
  file with a stub of the view.

## Extension files

Where the definition asks for hand-written code (a custom operation,
a custom page, a custom widget, and so on), the binding writes two
files ([ADR 0005](adr/0005-generation-gaps.md)):

- A generated file (`*.gen.ts`, `*.gen.tsx`, or `*_gen.py`) with the
  typed signature and the call. It has a `generated` trace.
- An extension file (`*.ext.ts`, `*.ext.tsx`, or `*_ext.py`) with a stub
  that the app developer replaces. It has a `gap` trace and a
  `TODO(appgen):` comment. An output rule with `extension=True` writes
  it.

The generator writes an extension file only if it does not exist, and
never changes or deletes it. The app must build and pass its type check
with the stubs. `appgen.bindings.shared.gaps` has helpers for the gap
files of the front ends (`gap_spec`, `gap_rules()`). The stub of a
custom UI element (a widget, a form widget, or a detail tab) shows its
element ID only in a development build (`process.env.NODE_ENV` in
Next.js, `import.meta.env.DEV` in React). A production build shows the
neutral text "Not available yet.".

The examples keep their hand-written code in
`examples/<example>/extensions/<binding>/`, with the paths of the app.
The check scripts copy these files into the app before they generate
it, so that the checks run the real code, for example a custom
operation that calls a third-party API.

A rule with `extension=True` can also write a file that is not a stub
but that belongs to the app after the first run. Give it a manual trace
(`trace("app", scope="file", kind="manual")`), not a gap trace. The
FastAPI binding writes its first migration in this way.

### Schema changes of the FastAPI app

The FastAPI app creates the first migration
(`migrations/versions/0001_schema.py`) once, and a new run keeps all
migrations ([ADR 0009](adr/0009-fastapi-schema-changes.md)). To change
the schema of a database that has data:

1. Change the app definition, and generate the app again into the same
   folder: `uv run appgen generate app.yaml -b fastapi -o <app>`.
2. In the app folder, make the next migration from the changed models:
   `uv run alembic revision --autogenerate -m "<change>"`. Alembic
   compares the models with the database of `DATABASE_URL`.
3. Review the new file in `migrations/versions/`. Edit it for the
   changes that Alembic does not find, for example a rename or a
   changed enum value.
4. Apply it: `uv run alembic upgrade head`. The data stays.

`scripts/check_schema_change.py` runs these steps on a copy of the
project tracker with SQLite, and checks that a record stays. The change
adds a field, and makes a field translatable: the next migration adds
the column of its translations
([ADR 0026](adr/0026-record-translations.md)).

## Shared templates

The Next.js and the React bindings share templates in
`src/appgen/bindings/shared/templates/`: the shadcn/ui components, the
theme, the app shell, the views, the forms, the dashboards, and the
entity types. Python modules next to them (`ui.py`, `views.py`,
`forms.py`, `details.py`, `dashboards.py`) compute the plans that the
templates render. A binding uses them with
`shared_template_dirs=(shared.TEMPLATE_DIR,)`. A template in the folder
of the binding with the same name wins over a shared template.

The shared UI code imports only `@/shared/*`, `@/widgets/*`,
`@/features/*`, and `@/entities/<entity>`. Each front-end binding
writes `@/shared/lib/router` (with `Link`, `useNavigate`, `usePathname`,
and `useParams`) and the entity slices with the same public API, so the
same UI code works with both routers and both data layers.

## Register the binding

Add an entry point in the group `appgen.bindings` in `pyproject.toml`,
and run `uv sync`:

```toml
[project.entry-points."appgen.bindings"]
mybinding = "appgen.bindings.mybinding:BINDING"
```

## Test and check the binding

- Add `tests/test_binding_<name>.py`: generate the example, check the
  important files, check that two runs give the same output, and check
  that `appgen check` finds no invalid traces.
- Add the binding to `BY_DESIGN` in `tests/test_end_to_end.py`, with
  the kinds that it excludes.
- Add `scripts/check-<name>.sh`: generate the example, install, lint,
  type check, build, run the tests of the app, `docker build`,
  `appgen check`, and the smoke test (`scripts/smoke_test.py`). Add the
  binding to the smoke test.
- Add the script and its path patterns to `.githooks/pre-push`.
- Pin the package versions of the generated app in a `versions.py`.
- Describe the binding in the README.

## Checklist

- [ ] Each generated file has a trace header, and each rendered element
      has a trace.
- [ ] `covers` lists all kinds that the templates render, and `excludes`
      lists the kinds out of scope.
- [ ] Hand-written code goes in extension files only.
- [ ] `extension_keys` declares each `x-` key that the binding reads.
- [ ] Two runs give the same output.
- [ ] The generated app builds with the stubs of the extension files.
- [ ] `appgen check` reports no invalid traces, and the expected
      coverage.
- [ ] The app has a Dockerfile, and uses uv (Python) or pnpm (TypeScript).
