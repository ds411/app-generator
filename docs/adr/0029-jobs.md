# 0029. Jobs on a schedule and at the time of a date field

- Date: 2026-10-26
- Deciders: Maintainers

## Status

Accepted

## Context

The generated apps run code only in requests. Many apps need work at a
later time: a reminder before a meeting or a due date, a recurring
invoice, a sync with a bank, an alert when a ticket waits too long, or a
weekly report. Without a scheduler in the apps, each app developer
writes one, and each replica of the app can run the same work again.

Two kinds of time are common. A schedule gives the same times for the
whole app, for example each Monday at 07:00. A date field gives a time
for each record, for example 24 hours before the start of a booking.

The constraints:

- The FastAPI app and the Next.js app run as more than one replica
  (ADR 0013). A job must run one time, not one time on each replica.
- The apps have a database (Postgres, or SQLite and PGlite on the local
  machine), and Redis only as an option for the rate limit. A new
  required service makes each deployment more difficult.
- The Next.js app has no long-running process: a request starts its
  code. The FastAPI app can start a second process from the same image.
- The logic of a job is code of the app, like the logic of a custom
  operation.

The options for the time zone of the schedules:

- **UTC.** The times are the same on each server and in each test. A
  schedule at 07:00 in Berlin is at 06:00 or 05:00 in UTC, by the
  season.
- **A time zone for each job, or for the app.** The times follow the
  local time, but a change of the clock (daylight saving time) skips an
  hour or repeats it, and each binding needs the rules of the time
  zones.

The options for the lock of a run:

- **A row for each run in a table of the database.** The key of the row
  is the job, the record, and the time. The first worker that inserts
  the row runs the job. The table also records the state of each run.
- **A lock in Redis, or an advisory lock of Postgres.** Redis is an
  extra service. An advisory lock does not exist in SQLite and PGlite,
  and records no state.
- **One worker only.** A second replica, for example during a
  deployment, runs the jobs again.

## Decision

We add an optional section `jobs`. A job runs on a cron `schedule` in
UTC, or `at` the time of a `date` or `datetime` field of each record
with an `offset`. A job with an entity calls a custom operation of the
entity on each record that its `filter` selects (the filter syntax of
the dashboards). A job without an entity is a generation gap.

- The schedules are in UTC. A cron expression has five fields, the
  names of the months and of the days, and the macros such as
  `@daily`. When both day fields are restricted, a day matches when one
  of them matches, as in Vixie cron and in Kubernetes CronJobs.
- An offset is a whole number with a sign and a unit (`m`, `h`, `d`, or
  `w`). A `date` field gives midnight in UTC.
- The operation of a job is a custom operation of the same entity,
  without a required param that has no default. The job calls it with
  the default params, so the logic stays in the extension file of the
  operation, and the endpoint and the job share it.
- `appgen validate` reports a job with `schedule` and `at`, or with
  neither (`invalid-option`, `missing-key`), a wrong cron expression or
  offset (`invalid-value`), a field of `at` that is not a stored date
  (`unsuitable-field`), an unknown operation (`unknown-reference`), and an
  operation that is not custom, of another entity, or with a required
  param (`unsuitable-operation`). The filter has the checks of the
  filters of the dashboards.
- A run is one job, one record (or none), and one time. The table
  `job_runs` keeps each run: its key (`<job>:<record or ->:<time in
  UTC>`), its state (`running`, `done`, or `failed`), the count of the
  attempts, the lock time, and the last error. The FastAPI app and the
  Next.js app have the same table and the same keys.
- A worker inserts the row of a run before it starts the run. The key is
  the primary key, so a second worker cannot insert it, also on another
  machine. A worker can take a failed run, or a run whose lock (10
  minutes) ended, with an update that checks the state.
- The work of a run and the state `done` are in one transaction. A
  failed run rolls back its work, gets the state `failed`, goes into the
  log with the job and the record, and runs again at the next run of the
  job.
- Each run of a job looks back over a window, 60 minutes by default
  (`JOBS_WINDOW_MINUTES`). A job with a schedule runs the last time of
  its schedule in the window. A job with `at` runs each record whose
  time is in the window. A change of the date field gives a new time,
  and so a new run. The times before the window do not run.
- The FastAPI app runs the jobs in a worker process, `python -m
  app.worker`, from the image of the API. A pass runs all jobs each
  `JOBS_INTERVAL_SECONDS` (60). The worker has a health endpoint on
  `WORKER_PORT`, and stops at SIGTERM. `--once --now <time>` runs one
  pass at a fixed time. The deployment files have a worker Deployment
  for Kubernetes and a Knative Service with one instance.
- The Next.js app runs each job in the route `/api/jobs/<job>`, with the
  secret `JOBS_SECRET`. A scheduler calls the route: a Kubernetes
  CronJob for each job with a schedule, and one each minute for the
  jobs with `at`. On Cloud Run, Cloud Scheduler calls the routes. A run
  is one transaction: in it, `getDb()` returns the transaction (an
  `AsyncLocalStorage`), so the repositories that the operation calls
  write in it. The route gives 500 when a run failed, so that the
  scheduler shows the failure. With `JOBS_FIXED_CLOCK=true`, the
  parameter `now` sets the time of a call, for the tests.
- The React app (mock data) has no jobs.

## Consequences

- An app gets reminders, recurring work, and reports without a
  hand-written scheduler and without a new service.
- Each run runs one time with any number of workers, and the table
  `job_runs` shows the state and the last error of each run.
- The window limits the work after a long stop of the workers: the
  older times do not run. A longer window catches up more, but a run of
  a job then reads more records.
- A schedule in UTC does not follow the daylight saving time. An app
  that needs a local time writes the schedule in UTC for each season,
  or checks the local time in the operation.
- A job calls its operation one record at a time, each in its own
  transaction. A job with many records runs as many transactions.
- A run that takes longer than the lock can run a second time on
  another worker. The logic of an operation should be safe to run again.
- The table `job_runs` grows with each run. The apps do not delete old
  rows.
- The first migration of an app has the table. An app that adds its
  first job later gets the table with the next migration
  (`alembic revision --autogenerate`).
