# 0005. Generation gaps

- Date: 2026-10-23
- Deciders: Maintainers

## Status

Accepted

## Context

A binding cannot generate all the code of an app. Examples are the
logic of a custom operation (ADR 0002), a custom widget or view
(ADR 0003), and the elements of a kind that the binding does not cover
(the binding contract, #26). The app developer writes this code by
hand. We call each such place a generation gap.

The generator runs again after each change to the definition. Thus
hand-written code and generated code must never overwrite each other.
The trace checker (M4) must also see which gaps are still open
(ADR 0004).

We looked at these options:

- **Protected regions** in generated files: the generator keeps the
  text between two markers when it writes the file again. The
  generated file then mixes the two kinds of code, a bad merge can
  lose hand-written code, and a byte-for-byte check of the output is
  not possible.
- **The Generation Gap pattern** (John Vlissides, "Pattern
  Hatching", 1998): the generator writes a base class, and the
  developer writes a subclass in a separate file that the generator
  never changes. The generated code and the hand-written code stay in
  separate files.
- **Partial classes** (C#): a language feature that TypeScript and
  Python do not have.

The plan of the PoC chose separate extension files that the generator
creates once and never overwrites. This ADR defines the details.

## Decision

### Two kinds of files

The generator writes two kinds of files:

| Kind           | Written                           | Changed by the developer | Deleted by the generator |
| -------------- | --------------------------------- | ------------------------ | ------------------------ |
| Generated file | On each run, the full content.    | Never.                   | Yes, when no rule writes it any more (#31). |
| Extension file | Once, only if the file is missing. | Yes, freely.             | Never.                   |

The output manifest (#31) lists the two kinds apart. A binding marks
an output rule as an extension rule. The generator renders an
extension rule only for a path that does not exist.

### File names

An extension file is next to the generated file that uses it, with a
name that shows its kind:

| Language   | Generated file           | Extension file           |
| ---------- | ------------------------ | ------------------------ |
| TypeScript | `<name>.gen.ts`          | `<name>.ext.ts`          |
| TSX        | `<name>.gen.tsx`         | `<name>.ext.tsx`         |
| Python     | `<name>_gen.py`          | `<name>_ext.py`          |

Python module names cannot contain a dot, so Python uses a suffix with
an underscore. Other generated files (for example `package.json`, a
Dockerfile, or a SQL migration) keep their usual names, because no
extension file goes with them.

Where a framework sets the file name (for example `page.tsx` in the
Next.js App Router), the framework file is a generated file with its
usual name. It imports the `.gen` and `.ext` modules next to it.

### How the generated code uses the extension code

The generated code imports the extension code, and never the reverse
direction for the same element. The binding generates the signature,
and the extension file gives the body:

- **Functions.** For a custom operation, the generated code imports a
  function with a fixed name from the extension file and calls it.
  The extension file, when the generator creates it, has the function
  with the generated signature and a body that fails with a clear
  TODO.
- **Components.** For a custom view, widget, or section, the generated
  component imports a component with a fixed name from the `.ext.tsx`
  file and renders it with typed props.
- **Overrides.** Where the developer must change a generated part, the
  generated module exports its parts, and the extension module can
  wrap them. The public entry of the module (for example the `index.ts`
  of an FSD slice) exports the extension version.

TypeScript example, for `operations.complete_task`:

```ts
// complete-task.gen.ts
// Generated by appgen. Do not edit: change the app definition instead.
// @trace operations.complete_task file
import type { Task } from "@/entities/task";
import { completeTask } from "./complete-task.ext";

export async function runCompleteTask(task: Task, note: string | null): Promise<Task> {
  return completeTask(task, note);
}
```

```ts
// complete-task.ext.ts
// Created by appgen once. appgen never changes or deletes this file.
// @trace:gap operations.complete_task file
import type { Task } from "@/entities/task";

export async function completeTask(task: Task, note: string | null): Promise<Task> {
  // TODO(appgen): write the logic of the operation complete_task.
  throw new Error("Not implemented: operations.complete_task");
}
```

Python example:

```python
# complete_task_gen.py
# Generated by appgen. Do not edit: change the app definition instead.
# @trace operations.complete_task file
from .complete_task_ext import complete_task
```

```python
# complete_task_ext.py
# Created by appgen once. appgen never changes or deletes this file.
# @trace:gap operations.complete_task file


def complete_task(task: Task, note: str | None) -> Task:
    # TODO(appgen): write the logic of the operation complete_task.
    raise NotImplementedError("operations.complete_task")
```

The extension file is not regenerated. Thus, if the signature changes
in the definition (for example a new param), the type checker of the
app (`tsc` or `pyright`) reports the difference between the generated
call and the old extension function. The developer then changes the
extension file.

### Elements that the binding does not cover

For an element of a kind that the binding does not cover (#26), the
generated code has no place to call. The binding declares one gap
rule: a template and a path for an extension file for each such
element, for example `src/gaps/<element ID>.ext.ts`. The file has the
gap trace, the description of the element, and a TODO. The developer
writes the code there, or moves it to a better place with the trace.

### The gap trace

A gap trace marks an element that needs hand-written code
(ADR 0004):

```text
@trace:gap <element ID> file
```

- The generator writes the gap trace in the header of each extension
  file that it creates, with a `TODO(appgen):` comment.
- When the developer writes the code, the developer changes
  `@trace:gap` to `@trace:manual`. The checker reports each element
  that has a gap trace as an open gap, also when the generated code
  that calls the extension has a `generated` trace to it (#151).
- An optional hook that works as it is (for example a validation
  function that accepts all records) is not a gap. Its extension file
  has a `@trace:manual` trace in the header.
- The generated file that calls the extension has a `generated` trace
  to the same element. Thus the checker sees both the generated part
  and the hand-written part.

### Elements that leave the definition

The generator never deletes an extension file. When the element of an
extension file leaves the definition (or gets a new name):

- The generator stops to write the generated code that imports the
  extension file. Thus no generated code uses it.
- The generator keeps the file, and the manifest keeps it in the list
  of extension files, marked as orphaned.
- The summary of `appgen generate` lists the orphaned extension files.
- The trace checker reports the traces in the file as invalid, because
  their element ID does not exist.
- The developer moves the code to the new extension file (after a
  rename), or deletes the file. At the next run, the generator removes
  a deleted extension file from the manifest.

## Consequences

- Hand-written code is never in a generated file, so the generator
  can write generated files byte for byte, and a regeneration never
  loses hand-written code.
- The type checker of the app finds an extension file that no longer
  agrees with the generated signature.
- Each gap adds a file and an import. The app has more files.
- Orphaned extension files stay until a developer removes them. The
  summary and the trace checker report them, so they do not stay
  unseen.
- The developer must change `gap` to `manual` in the trace. If the
  developer forgets, the checker reports an open gap for written code.
- A binding must name its extension rules and its gap rule. The
  binding contract gets these fields in #29.
