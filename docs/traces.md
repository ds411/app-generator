# Traces and the trace checker

A trace is a comment in the code of an app that refers to an element of
the app definition, for example `// @trace entities.Task.fields.title`.
The generator writes traces into the code that it generates, and app
developers write traces into the code that they write by hand.
`appgen check` reads the traces of an app and reports what the code
covers and what is wrong. [ADR 0004](adr/0004-trace-format.md) and
[ADR 0005](adr/0005-generation-gaps.md) give the reasons for the
design.

## Trace format

```text
@trace[:<kind>] <element ID> [<scope>]
```

- `kind` is `generated` (the default), `gap`, or `manual`.
- The element ID is the ID of a definition element
  ([dsl.md](dsl.md#names-and-ids)), for example `operations.complete_task`.
- `scope` is `file`, `begin`, or `end`. Without a scope, the trace is a
  line trace.
- One trace has one ID. Text after the trace on the same line is not a
  part of it.

Examples:

```text
@trace app file
@trace entities.Task.fields.title
@trace:gap operations.complete_task file
@trace:manual operations.complete_task
@trace ui.views.task_table.columns.title begin
@trace ui.views.task_table.columns.title end
```

## Kinds

| Kind        | Who writes it | Meaning                                                    |
| ----------- | ------------- | ---------------------------------------------------------- |
| `generated` | The generator | This code comes from the element.                          |
| `gap`       | The generator | The element needs hand-written code here.                  |
| `manual`    | The developer | This hand-written code covers the element.                 |

For the coverage, an element with a `gap` trace is an **open gap**, an
element with a `generated` or a `manual` trace and no `gap` trace is
**covered**, and an element without a trace is **uncovered**. A `gap`
trace keeps the element open also when other traces refer to it: the
generated code that calls a stub has a `generated` trace to the element
of the stub, but the stub still needs hand-written code. A trace covers only its
own element: a trace to an entity does not cover the fields of the
entity.

## Scopes

| Scope | Written as                          | Applies to                                         |
| ----- | ----------------------------------- | -------------------------------------------------- |
| File  | `@trace <id> file`                  | The whole file. Only in the header of the file.    |
| Block | `@trace <id> begin` ... `@trace <id> end` | The lines between the two traces. Blocks can nest, but not overlap. |
| Line  | `@trace <id>`                       | The line of the trace if it follows code, else the next line of code. |

The header is the comment lines and blank lines at the top of the file.
A shebang, a Python encoding line, or a Dockerfile parser directive can
come before it. Each generated file starts with a header:

```ts
// Generated by appgen. Do not edit: change the app definition instead.
// @trace entities.Task file
```

## Comment syntax

The trace must follow a comment opener on the same line. The checker
does not read traces in strings, or in the later lines of a multi-line
comment. For such `@trace` text with an element ID, the report shows a
warning with the file and the line (see [Warnings](#warnings)). In
Markdown files, the text in code spans and fenced code blocks is an
example, so it gives no warning.

| File type                | Trace comment                                   |
| ------------------------ | ----------------------------------------------- |
| TypeScript, JavaScript   | `// @trace ...` or `/* @trace ... */`           |
| TSX, JSX                 | `// @trace ...`, and `{/* @trace ... */}` in JSX |
| Python                   | `# @trace ...`                                  |
| SQL                      | `-- @trace ...`                                 |
| CSS                      | `/* @trace ... */`                              |
| Dockerfile, YAML, TOML, shell, `.env` | `# @trace ...`                     |
| Markdown, HTML           | `<!-- @trace ... -->`                           |

Files without comments, for example `package.json`, get their traces
from the manifest.

## Generation gaps

Where the definition asks for code that a binding cannot generate (a
custom operation, a custom page or widget, a custom form rule, and so
on), the generator creates an **extension file** with a stub, a gap
trace, and a `TODO(appgen):` comment:

```python
# Created by appgen once. appgen never changes or deletes this file.
# @trace:gap operations.complete_task file
...


async def complete_task(session: AsyncSession, record: Task) -> Task:
    # TODO(appgen): write the logic of the operation complete_task.
    raise NotImplementedError("operations.complete_task")
```

The generated code next to it (`*_gen.py`, `*.gen.ts`) calls the
function. The app builds with the stub. To fill the gap:

1. Write the code in the extension file.
2. Change `@trace:gap` to `@trace:manual` in its header.
3. Run `appgen check`: the element is covered, not an open gap.

While the header has `@trace:gap`, the checker reports the element as an
open gap, also when generated code calls the stub.

An extension file can also be an optional hook that works as it is, for
example the `validation_ext.py` of an entity in the FastAPI binding (by
default it accepts all records). The definition does not ask for a
hook, so it is not a gap: its header has a `@trace:manual` trace.

The generator writes an extension file only if it does not exist, and
never changes or deletes it. Thus a new run keeps the hand-written code.

## The manifest

`appgen generate` writes `.appgen/manifest.json` into the output
folder. It lists each generated file with its SHA-256 hash and its
traces, each extension file, and the element kinds that the binding
excludes. The generator uses it to find generated files with manual
edits (it stops, unless `--force`), and the files to delete. The checker
uses it for the traces of files without comments, and to find
`generated` traces in files that appgen did not generate.

## The checker

```sh
uv run appgen check <definition> <code-folder> [options]
```

| Option                  | Effect                                                            |
| ----------------------- | ----------------------------------------------------------------- |
| `-f`, `--format`        | `text` (default) or `json`.                                       |
| `--min-coverage <n>`    | Fail if the coverage in percent is lower than `n`.                |
| `--exclude-kind <kind>` | Do not count the elements of this kind and the elements under them. Repeat for more kinds. |
| `--ignore <pattern>`    | Skip more paths (gitignore syntax). Repeat for more patterns.     |
| `--no-gitignore`        | Also scan the paths in `.gitignore` files.                        |

The checker scans the files of the folder with a text scan. It skips
the paths in `.gitignore` files and tool folders such as
`node_modules/`, `.venv/`, and `.git/`. The kinds that the manifest
lists as excluded are excluded too.

| Exit code | Meaning                                                           |
| --------- | ----------------------------------------------------------------- |
| 0         | The check passes.                                                 |
| 1         | There is an invalid trace, or the coverage is lower than `--min-coverage`. |
| 2         | The definition or the manifest is not valid.                      |

An uncovered element or an open gap does not fail the check by itself.
Use `--min-coverage` to fail on them.

## The text report

The report of the FastAPI app of the project tracker:

```text
Trace check: 108 files, 376 traces.

Invalid traces: 0

Uncovered elements: 0

Open gaps: 3
  operations.archive_project (operation): app/features/projects/archive_project_ext.py:2
  operations.assign_task (operation): app/features/tasks/assign_task_ext.py:2
  operations.complete_task (operation): app/features/tasks/complete_task_ext.py:2

Coverage:
  kind       covered  gaps  uncovered  coverage
  app              1     0          0   100.0 %
  entity           4     0          0   100.0 %
  field           20     0          0   100.0 %
  relation        10     0          0   100.0 %
  operation       18     3          0    85.7 %
  param            2     0          0   100.0 %
  all             55     3          0    94.8 %
  Excluded kinds: page, ui.

Result: passed.
```

The report has these parts:

- **Invalid traces**: each one with its file, line, column, and reason.
- **Warnings**: the trace text that the scan does not read, each one
  with its file, line, and column. The report shows this part only if
  there is a warning.
- **Uncovered elements**: the elements without a trace.
- **Open gaps**: the elements with a gap trace, and where the gap
  traces are.
- **Coverage**: the counts and the percentage for each element kind,
  and in total, and the excluded kinds.
- **Result**: `passed` or `failed`.

## The JSON report

`--format json` writes a stable document for tools. The same report
gives the same text. A change that breaks readers changes `version`.

```json
{
  "version": 1,
  "passed": true,
  "files": 108,
  "traces": 376,
  "invalid": [],
  "warnings": [],
  "uncovered": [],
  "gaps": [
    {
      "id": "operations.archive_project",
      "kind": "operation",
      "traces": [{ "file": "app/features/projects/archive_project_ext.py", "line": 2 }]
    }
  ],
  "coverage": {
    "percent": 94.83,
    "total": 58,
    "covered": 55,
    "gaps": 3,
    "uncovered": 0,
    "min_percent": null,
    "excluded_kinds": ["page", "ui"],
    "by_kind": [{ "kind": "app", "percent": 100.0, "total": 1, "covered": 1, "gaps": 0, "uncovered": 0 }]
  }
}
```

An entry of `invalid` or of `warnings` has `file`, `line`, `column`,
`code`, `message`, `text`, `element_id`, and `hint`. An entry of
`uncovered` has `id` and `kind`. An entry of `gaps` has `id`, `kind`,
and `traces`: the `file` and `line` of each gap trace. `coverage.gaps`
and `gaps` in each entry of `by_kind` give the number of open gaps for
each element kind.

## Invalid traces

The checker reports these traces as invalid:

- A trace to an element ID that the definition does not have, for
  example after a rename. The report adds a "did you mean" hint for a
  similar ID.
- A trace with an unknown kind or scope.
- A file trace outside the header.
- A `begin` without its `end`, an `end` without its `begin`, or an
  `end` that does not agree with the innermost open block.
- A `generated` trace in a file that the manifest does not list as
  generated, for example code that a developer copied into an
  extension file.

## Warnings

The checker shows a warning (code `skipped-trace`) for `@trace` text
with an element ID that the scan does not read, because it does not
follow a comment opener on the same line:

```text
Warnings: 1
  src/a.ts:3:12: skipped-trace: The scan does not read this trace: it does not follow a comment opener on the same line.
    @trace entities.Task
    hint: Put the trace in a comment of its own line, for example '// @trace entities.Task'.
```

A warning does not change the result or the exit code. The generated
apps give no warnings.

## After a change to the definition

When the definition changes, `appgen generate` writes the generated
files again, deletes the generated files that no rule writes any more,
and keeps the extension files. Hand-written code can then refer to
elements that the change renamed or removed. The checker reports these
traces as invalid, so the drift shows:

```text
Trace check: 109 files, 383 traces.

Invalid traces: 3
  app/features/comments/validation_ext.py:2:3: unknown-element: The definition has no element 'entities.Comment'.
    @trace:manual entities.Comment file
    hint: Did you mean 'entities.Project'?
  app/features/tasks/complete_task_ext.py:4:3: unknown-element: The definition has no element 'entities.Comment'.
    @trace:manual entities.Comment
    hint: Did you mean 'entities.Project'?
  app/features/tasks/complete_task_ext.py:5:3: unknown-element: The definition has no element 'pages.people'.
    @trace:manual pages.people
    hint: Did you mean 'pages.projects'?

...
Result: failed: 3 invalid traces.
```

The hint compares the spelling of the IDs, so after a rename it can
name a wrong element, as above. The first file is the validation
extension file of the old entity: the generator keeps it, but no
generated code uses it any more. The developer moves the code to the new
element (after a rename) and changes its traces, or deletes the code. `tests/test_definition_change.py`
tests this for each binding.
